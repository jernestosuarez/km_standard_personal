# Proposal: promote-external-build-mechanisms (v1.62 draft)

**Nothing here binds until this version's own owner push.**

## Why

The deployment owner directed (2026-08-27) that the improvements demonstrated by an external
application build be integrated into the standard. A promotion inventory run the same week — the
first assessment ever made of that build's accepted work — classified twenty-two accepted slices,
settled seventeen as application-specific with no canonical governing section able to own them, and
shortlisted five mechanisms. The inventory deliberately stopped short of the promotion assessment
itself; this change runs it.

Each of the five was assessed three ways before any drafting: **duplication** against the current
canonical text, by property search in both case forms with known-positive controls; **checkability**,
with a real negative test named, or the absence of any mechanical check stated plainly; and the
**generic-organisation test** — would the mechanism help an organization that has never heard of
this deployment. Four survived. The fifth returned **no-change**, and the reason is published in the
version row rather than dropped, per this repository's own rule that what does not survive
verification is recorded beside what does.

Authority: a direct instruction from the deployment owner, relayed through the Supervisor's ledger
(`std-0016`), following the inventory record (`std-0015`). Evidence: the build's accepted records
`9f52225`, `10d3425`, `ebf0fae`, `25609c4`, `d6f1873`, read from committed history and genericised.
No organization, person or initiative is named in any canonical line this change adds.

## What Changes

1. **A consuming answer surface discloses nothing it will not answer** — a new subsection of Rule 6,
   drafted as a **reconciliation** with crossing law 3 (*existence crosses; contents don't*) rather
   than grafted beside it. Restricted-beyond-clearance, ineligible-evidence and genuinely-absent
   render as one byte-identical no-answer state on a consuming answer surface, because a
   differentiated refusal is an oracle. Law 3 stands untouched between governed parties. **This
   narrows published doctrine and requires the owner's explicit word at publication; the subsection
   says so where it is drafted.**
2. **The diagnostic record** — a new subsection of the correction loop giving "the mistake was
   diagnosed" a definition: four required sections, protecting the rule that a shared failure value
   is not a shared cause. The confounded-comparator and route-qualified-causality lessons from the
   same build land here, in the matrix and hypothesis sections, where the evidence itself holds them.
3. **The acceptance threshold and the stop predicate are fixed before the measurement runs** — a new
   paragraph beside the v1.61 deferral rule. The mechanical half is commit ordering; what ordering
   cannot prove is stated with it.
4. **A cache may accelerate feedback; it never produces the authoritative verdict** — a new paragraph
   beside the release gate. **The scope question — whether this standard should govern a tooling
   class it does not ship — is stated in the paragraph for the owner rather than resolved silently.**
5. **No-change** for per-criterion evidence pointers on acceptance criteria: the assessment could
   not produce a report the pointer catches that the maintainer contract's existing obligations
   miss, and the claimed instrument (`[ LINKS ]`) would never read an acceptance record, so the
   checkability claim did not survive inspection.

## Impact

- `STANDARD.md` only, plus this OpenSpec package. No check is added or changed; no template, skill,
  script or agent contract restates the changed obligations (swept: the template instruction files'
  "when it is diagnosed" line and the architecture note's law-3 restatement are consistent with the
  grafts, and the maintainer contract's criteria obligations are named as instances, not amended).
- Every added rule that has no mechanical check says so in its own text. No new instrument, so no
  unrepaired-tree declaration is owed.
- Deployments are unaffected until the owner push; v1.23 remains drafted; the version ledger gains
  one drafted row.
