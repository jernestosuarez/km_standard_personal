# Design: promote-external-build-mechanisms (v1.62 draft)

**Nothing here binds until this version's own owner push.**

## The assessment, run in full, in inventory rank order

The inventory that shortlisted these five explicitly did not assess them. This change runs the full
promotion assessment per candidate: duplication, checkability, generic-organisation. The duplication
sweeps were run as direct single invocations after a loop construct was caught returning an
identical implausible count for four different terms — the malformed-query class this estate has
already recorded, met again in the assessing session itself. Known-positive control: `provenance`,
56 files. Known-negative control: a nonsense token, 0 files.

### Candidate 1 — restricted, ineligible and absent indistinguishable on a consuming surface

- **Duplication:** `indistinguishable` appears in 17 files, none about disclosure states;
  `no-answer` and `reader-visible` appear nowhere. The property is absent from canonical.
- **The collision, which is the whole difficulty:** crossing law 3 (v1.22, published) and its v1.23
  scale-invariant restatement permit existence disclosure everywhere; the promoted rule forbids it
  on one surface class. Drafted as a reconciliation: the boundary is who the surface serves —
  stewardship (existence crosses) versus consumption at or below clearance (a differentiated refusal
  is an oracle; existence is the leak). The owner-adjudicated `shareable/` artifact is named as
  neither: a human act under the proposal flow, not a mechanical answer path.
- **Checkability:** negative test named — byte-identical output for a restricted-only topic and an
  absent one; a test asserting any differentiated refusal state must fail. Honest status: no shipped
  instrument evaluates a serving surface (the MCP surface is quarantined and serves nothing), so the
  rule is convention until an implementation ships the byte-identity case with it. The quarantine's
  own lift criteria gain their missing definition of "unreachable": the same bytes as absence.
- **Generic test:** any organization running an answer surface over a governed corpus faces the
  differential-oracle problem. Survives.
- **Doctrine:** because this narrows law 3's reach, the subsection states that the owner push
  publishing the version is the explicit doctrine word, given knowingly.

### Candidate 2 — the diagnostic record, and shared-value-is-not-a-shared-cause

- **Duplication:** `diagnostic` 0 files, `hypothesis` 1 (unrelated), `falsif` 15 (all about
  falsified assertions, none about falsifying evidence for a hypothesis), "shared cause" 0.
  Canonical's correction loop says a mistake "was diagnosed" and defines nothing.
- **Evidence:** five independent investigation records of the external build converged on the same
  four-section shape, and an estate independently minted the identical shared-value rule from its
  own incident — the promotion sweep's own strongest signal, the same principle in two places that
  have never heard of each other.
- **Checkability:** section presence is checkable by a deployment that adopts a fixed heading set;
  hypothesis quality, matrix validity and confidence honesty are judgements no evidence in a tree
  represents. The draft says both, and this standard ships no instrument that reads diagnostic
  records — stated, not implied.
- **Folded rows:** confounded-comparator (one variable per comparison; a confounded comparison is
  evidence for neither reading) and route-qualified causality (the hypothesis is scoped no broader
  than the route that established it) land in sections 2 and 3 of the form, because the diagnosis
  record that evidences the form demonstrates both.
- **Generic test:** survives; nothing in the form names a toolchain.

### Candidate 3 — threshold and stop predicate fixed before the measurement

- **Duplication:** "stop predicate", "before the measurement", "acceptance threshold" all 0;
  `threshold` hits govern other things (hub count, staleness, per-token gates). The maintainer
  contract's "define acceptance criteria before editing" is the nearest neighbour and is named in
  the draft as an instance, not amended.
- **Evidence:** three independent design commits of the external build carried binding thresholds
  and stop conditions before their measurement runs (a cache value gate with warm/cold thresholds
  and rollback sentinels; a benchmark with a binding acceptance threshold and a pre-committed
  removal rule on failure; a repair plan with stop conditions).
- **Checkability:** the mechanical half is exactly two git questions — ancestry and containment —
  and the draft states what they cannot prove: an unrecorded prior run, a stop predicate honoured,
  a threshold well chosen. No such check ships in this change.
- **Graft site:** beside the v1.61 deferral rule, whose measured-not-estimated test is the same
  line drawn for difficulty; this draws it for acceptance.

### Candidate 4 — a cache never produces the authoritative verdict

- **Duplication:** every `cache` hit in canonical concerns the publisher's out-of-tree environment
  or the cockpit; no rule about memoised verification exists, and no build-tooling vocabulary
  exists at all — which is the scope question, and it is the owner's, stated first in the
  paragraph rather than resolved by drafting.
- **Evidence:** one accepted instance (which is why it ranks last): a governed local task cache
  whose acceptance kept the authoritative gate direct and uncached and said so in the record, with
  invalidation proven in both directions.
- **Checkability:** the negative test is named (a defect the key does not capture must be caught by
  the direct run; invalidation proven in both directions). Nothing in this repository can check a
  deployment's cache; the obligation lives in the deployment's acceptance record, where the direct
  run's command line is the evidence. The one statement available here — this gate discovers and
  executes on every run — is a fact about the instrument, not a control, and the draft says so.
- **Generic test:** survives; the rule names a tooling class, not a tool.

### Candidate 5 — per-criterion evidence pointers: no-change

The test the assessment set itself: produce a verification report the pointer catches that the
existing obligations miss. It could not. The maintainer contract requires criteria defined before
editing and verified individually afterward, forbids describing an unrun check as passing, and
v1.61 already binds that a verification declaration is a record of what was run — a bare
"criterion 3: PASS" records nothing of what was run and already fails that rule's natural reading.
The residue the pointer would add is form, not coverage. The inventory's checkability claim also
failed inspection: `[ LINKS ]` resolves frontmatter wiki-links of monitored entity notes and would
never read an acceptance record's body, so selling the pointer as checkable by an existing
instrument would be a false assurance. Verdict: **no-change**, published in the version row. The
confounded-comparator and route-qualified-causality rows the inventory folded into this candidate
survive inside candidate 2, where the evidencing record itself holds them.

## What this change deliberately does not do

- It adds no instrument. Each added rule that has no mechanical check says so in its own text,
  because a procedural control described as mechanical is a false assurance.
- It does not amend the maintainer contract, the template, any skill or any check: the sweep found
  no shipped surface restating the changed obligations in a way the grafts contradict.
- It does not resolve the two owner questions. The candidate-1 doctrine word and the candidate-4
  scope word are stated in the drafted text and are answered by the owner push that publishes the
  version — or by amendment of this draft before it.
